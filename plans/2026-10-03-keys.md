# Keys: one vault for every AI API key

Status: done (shipped 2026-10-03 overnight — see features/keys.md)

## Why

Sal reuses the same Anthropic / OpenAI / ElevenLabs / etc. keys across ~30 projects, pastes
them into chat, and loses track of which key lives where. He wants:

- one place that knows every AI API key, **one key per project per provider**
- to mint a fresh key for a project, for real, where the provider's admin API allows it;
  otherwise open the provider's console page and capture the key without it ever passing
  through a chat transcript
- any Claude session to handle "make me a new ElevenLabs key for pickleball" on its own
- the key written into that project's gitignored `.env`, which is how every app reads it

Providers are **arbitrary**: a handful are built in, and Sal can add any other one (name,
env var, console URL) from the screen or CLI.

## Decisions (Sal, 2026-10-03; settled)

- **Lives in destedtui**: a TUI screen plus a third global bin, `keys`.
- **Mint where possible**, register by paste otherwise. Each key belongs to one project.
- **Storage**: one vault file encrypted with Windows DPAPI (CurrentUser scope), at
  `~/.destedtui/keys/vault.bin`. Use `CryptProtectData`/`CryptUnprotectData` from crypt32
  through bun:ffi (the repo already does bun:ffi in `lib/ports.ts`). No master password.
  Write atomically (tmp + rename) and keep the last 5 versions as `vault.bin.<n>`.
- **Distribution**: `keys env <project>` writes or updates that project's keys in its
  root `.env`. Preserve every other line and comments, make sure `.env` is gitignored
  (add it if not), and never commit.
- **Claude must know about it** (global CLAUDE.md + a skill), and so must PowerShell.

## Shape (the builder decides details, not these)

### Data (zod-validated after decrypt)

- `providers[]`: `id` (slug), `name`, `envVar` (e.g. `ELEVENLABS_API_KEY`), `consoleUrl`
  (the page where a human creates a key), optional `mint` adapter id, `builtin` flag.
- `keys[]`: `id`, `providerId`, `project` (folder slug under `G:\code`, or `"shared"`),
  `label`, `value`, `fingerprint` (sha256 prefix, shown instead of the value), `createdAt`,
  `source` (`minted` | `pasted` | `imported`), `remoteId` (needed to revoke), `revokedAt`.
- `admin[]`: admin/management credentials per provider, which mint adapters use. Stored the
  same way, and never written to any `.env`.

### Built-in providers

Anthropic, OpenAI, ElevenLabs, Google Gemini, xAI, Groq, OpenRouter, Replicate, fal.
**Research each provider's current admin API** (don't trust memory; fetch the docs):

- OpenAI: the `openai-image` skill (`~/.claude/skills/openai-image/`) already mints and
  revokes keys from `OPENAI_ADMIN_KEY` (project service accounts). Reuse that approach.
- ElevenLabs: check whether workspace/service-account API key creation exists and what it
  needs. If it doesn't exist, it's console-only.
- Anthropic: the Admin API can list, update and archive keys; as far as we know it can't
  create them. Verify. If creation is impossible, it's console-only, plus archive on revoke.
- Others: console-only unless the docs show a key-creation endpoint.

A mint adapter is a small module: `mint(admin, {project, label}) → {value, remoteId}` and
`revoke(admin, remoteId)`. Adding one later must be a one-file change.

### `keys` CLI (non-interactive first: Claude sessions drive it)

- `keys list [--project p] [--provider x]`: fingerprints only, never values
- `keys new <provider> --project p [--label l]`: mint if an adapter and admin credential
  exist; otherwise open `consoleUrl` in the browser and print the exact next step
- `keys add <provider> --project p --clipboard`: read the key from the clipboard, store
  it, then clear the clipboard. This is how a console-created key gets in **without the
  secret entering a Claude transcript**. Also allow `--stdin`. Never accept the value as
  an argv token.
- `keys env <project> [--dry-run]`: write that project's active keys into its `.env`
- `keys revoke <id>`: remote revoke via adapter where possible, mark `revokedAt`, and
  remove the line from the project's `.env`
- `keys providers` / `keys provider add <id> --name --env-var --console-url`
- `keys admin set <provider> --clipboard`
- `keys import`: scan `G:\code\*\.env` (top level of each repo plus a shallow walk; reuse
  `lib/discovery.ts` SKIP_DIRS) for known env vars and for any `*_API_KEY`/`*_TOKEN`
  matching a provider. Store each value as `imported` and print a **reuse report**: the
  same fingerprint in N projects. That report is the mess Sal wants untangled; the screen
  shows it too.
- `keys reveal <id>`: only with `--yes-print-secret`. Claude never runs it.
- Exit codes: 0 ok, 1 user error, 2 provider/API error. `--json` on list/import/new.

### TUI screen (`Keys`)

Route plus a main-menu tile plus a picker action (type `keys`), and `destedtui --keys`.
Follow ui.md and the existing screens (ListPicker, Footer hints, the replace-not-overlay
editor pattern from CommandEditor). It shows keys grouped by project or provider (toggle),
with reuse warnings (`⚠ same key in 4 projects`), and these actions: new/mint, add from
clipboard, revoke (two-press like Ports kill), write to `.env`, open console, add provider,
set admin credential. Values are never shown; fingerprints only.

### Claude + PowerShell wiring

- **Skill** `keys` (source in this repo, e.g. `skill/keys/SKILL.md`, junctioned into
  `~/.claude/skills/keys` by `--install-shell` or the README step). It triggers on "new
  key", "make me a key", "API key", "rotate the key", "which key does X use", and "key
  pasted in chat". The flow: `keys new` → if console-only, tell Sal to copy the key and
  say "done" → `keys add --clipboard` → `keys env`. It must never print, echo or paste a
  key value, and never read one out of `.env` into the transcript.
- **Global CLAUDE.md**: edit `G:\code\sals-powershell-setup\claude\CLAUDE.md` (never the
  `~/.claude/CLAUDE.md` shim). Add a short "API keys: use `keys`" section: never reuse a
  key across projects, never ask Sal to paste a key into chat, mint with `keys new`. In
  the same edit, add a short "Personal agent: sal-agent" section: `G:\code\sal-agent`, the
  `sal` CLI (`sal remind|next|note|waiting|brief`), its daemon (Task Scheduler), the
  `sal-agent` skill, and the upcoming voice page (`sal voice`, http://localhost:4747).
  Keep both terse and in the file's voice.
- **PowerShell** (`sals-powershell-setup`, read its `cliffnotes.md` first): make the
  profile aware of both tools. Tab completion for `keys` subcommands and project names is
  nice to have. Add a `Use-Keys <project>` helper that loads a project's keys into the
  current session's env without writing a file, plus a mention of `sal`. Document both in
  that repo's cliffnotes. If `install.ps1` should link the keys skill, do it there.
